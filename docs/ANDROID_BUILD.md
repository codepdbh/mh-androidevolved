Proyecto Java/Gradle para Android 10+, SDK de compilación 35, plugin Android 8.10.1 y arquitectura ARM64. El launcher usa Storage Access Framework y conserva permiso de lectura. Calcula SHA-256 del `manhunt.exe` directamente presente en la carpeta y reconoce el hash inventariado; no verifica los demás archivos ni acredita compatibilidad. Muestra una vista previa de controles y deja desactivado el botón de jugar.

El launcher carga `libmh_runtime.so` mediante JNI y pide una comprobación básica de memoria sobre un búfer de prueba. Para el ejecutable identificado vuelve a verificar el hash y solicita al código nativo un mapeo PE y enumeración de importaciones en memoria, sin ejecutar el archivo ni escribirlo. No resuelve las importaciones. Son diagnósticos: no validan el runtime completo. El archivo Java compiló por separado contra Android 35. La biblioteca JNI se compiló y enlazó para AArch64 tanto directamente con Clang como mediante el CMake del proyecto; se comprobaron ambas exportaciones JNI. Un arnés con tabla JNI simulada en Windows x64 verificó el diagnóstico, el rechazo por tamaño y el mapeo de PE válido e inválido; el hash del archivo original no cambió. Este arnés no sustituye una prueba Android: la biblioteca no se ha cargado en Android ni se ha probado su ciclo de vida.

El supervisor admite una compilación Gradle 8.11.1 offline con un trabajador y límites por Job Object, y exige 4096 MiB de memoria libre. No se ha ejecutado por presión de memoria; su árbol real sigue sin comprobarse. La ruta CMake nativa sí se probó con un trabajador y un límite de 512 MiB: el primer intento agotó la cuota de cuatro procesos al iniciar el enlazador; con ocho procesos máximos completó. No existe wrapper ni APK y no se ha ejecutado la aplicación en un dispositivo.

Se prepararon dos ejecutables ARM64 de pruebas sintéticas en `build/device-tests/`, con hashes en su manifiesto. Ambos pasaron en un Galaxy S25 Ultra (`SM-S938B`) sin datos comerciales ni gráficos; ver `docs/evidence/S25_ARM64_SYNTHETIC_TESTS.md`. No son una APK ni una prueba de gameplay.

Para una prueba autorizada en un Galaxy S25, el supervisor exige un único dispositivo ADB autorizado, verifica modelo y ABI, crea un directorio temporal propio, copia solo esos dos binarios, comprueba sus hashes y los ejecuta. Después elimina exactamente esos archivos y su directorio, sin borrado recursivo. Si el teléfono se desconecta, la limpieza puede fallar y debe revisarse el registro. El flujo se ha probado tanto con ADB simulado para rechazo y limpieza como en el S25 indicado arriba.

Hay además una prueba sintética ARM64 de despacho, compilada y verificada, con un perfil separado para comprobar llamadas válidas y fallos esperados. Un intento real se interrumpió por un reinicio de ADB antes de ejecutar la prueba; posteriormente una inspección de solo lectura no encontró directorios temporales del proyecto. Se preparó un perfil de una sola sesión para transferir, verificar, ejecutar y limpiar; pasó pruebas simuladas y de sintaxis, pero su intento real quedó aplazado por memoria insuficiente. La prueba de despacho todavía no está probada en Android.
